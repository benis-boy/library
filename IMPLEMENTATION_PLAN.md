# Comment Reply Notifications Implementation Plan

## Goal

Add minimal per-user notifications for comment replies.

A logged-in user should see a header bell with an unread count. Opening it shows recent reply notifications, marks the inbox as checked explicitly, and lets the user navigate to the exact comment thread location.

This feature is pull-only. It does not use push notifications, browser notifications, websocket updates, or periodic polling.

## Current Architecture Notes

- Auth identity comes from `PatreonContext`.
- `signedUser` is currently `HMAC(userName)` generated by `netlify/functions/patreon-oauth/patreon-oauth.js`.
- Comment mutations are handled by `netlify/functions/comments/comments.js`.
- Comment ownership is stored as `mutationOwner` in DB and is already verified before writes.
- Thread data includes:
  - `locationId.bookId`
  - `locationId.chapterId`
  - optional `locationId.paragraphLocation`
  - `rootCommentId`
  - `commentsById`
- `ParagraphLocation` already contains `paragraphIndex`; do not duplicate it.
- Existing `GET ?commentIds=...` currently fetches reactions, not comment bodies.
- To load notification comment bodies, use notification `location` plus existing thread-fetching APIs and extract `parentCommentId` / `replyCommentId` from returned `commentsById`.

## Notification Payload

Store only routing and lookup data. Do not store parent/reply text snapshots.

Each notification must contain the thread location plus both comment ids needed by the UI. The parent and reply are expected to be in the same logical thread because replies are inserted into the parent comment's containing thread.

```ts
type CommentReplyNotification = {
  id: string;
  type: 'comment-reply';
  createdAt: number;

  actorUserName: string | null;

  locationId: ThreadLocationId;
  parentCommentId: CommentId;
  replyCommentId: CommentId;
};
```

Redis Storage
Use Redis sorted sets per recipient.
Keys:
notifications:v1:user:{signedUser}:items
notifications:v1:user:{signedUser}:last-checked-at
notifications:v1:users
Details:
- items is a sorted set.
- Score is createdAt.
- Member is the notification JSON string.
- last-checked-at is a number timestamp.
- users is a set of signed user keys that have notification inboxes, used by manual cleanup.
Auth Transport
Do not pass signedUser in URL query params.
Even though HTTPS encrypts the request in transit, query params can leak into browser history, server/CDN logs, analytics, referrers, and screenshots.
Use headers for notification read endpoints:
Authorization: Bearer {signedUser}
X-Comment-User-Name: {userName}
Update CORS headers in comments.js:
Access-Control-Allow-Headers: Content-Type, Authorization, X-Comment-User-Name
For POST mutations, keep using JSON body mutationOwner.
Backend API
Extend netlify/functions/comments/comments.js.
Read Summary
GET /comments?notifications=summary
Authorization: Bearer {signedUser}
X-Comment-User-Name: {userName}
Response:
{
  unreadCount: number;
  lastCheckedAt: number;
}
Behavior:
- Verify header auth by checking signUserName(userName) === signedUser.
- Read lastCheckedAt, default 0.
- unreadCount = ZCOUNT inbox (lastCheckedAt +inf.
Read List
GET /comments?notifications=list&limit=5&before={createdAt}
Authorization: Bearer {signedUser}
X-Comment-User-Name: {userName}
Response:
{
  items: CommentReplyNotification[];
  unreadCount: number;
  lastCheckedAt: number;
  nextCursor: number | null;
}
Behavior:
- Verify header auth.
- Default limit to 5.
- Cap limit to a small max, e.g. 20.
- If no before, return newest items.
- If before exists, return items older than that timestamp.
- Use ZREVRANGE / ZREVRANGEBYSCORE.
- nextCursor is the createdAt of the last item if another page may exist.
Mark Checked
POST /comments
Request:
{
  notificationAction: 'mark-checked';
  mutationOwner: {
    userName: string;
    signedUser: string;
  };
}
Response:
{
  lastCheckedAt: number;
  unreadCount: number;
}
Behavior:
- Verify mutationOwner.
- Set lastCheckedAt = Date.now().
- Return updated summary.
Manual Cleanup
POST /comments
Request:
{
  notificationAction: 'cleanup';
  adminSecret: string;
}
Behavior:
- Verify adminSecret === process.env.NOTIFICATIONS_ADMIN_SECRET.
- Iterate notifications:v1:users.
- For each user inbox:
- Always keep newest 10.
- For entries older than 180 days outside the newest 10, remove them.
- Return cleanup stats.
Response:
{
  scannedUsers: number;
  deletedNotifications: number;
}
Implementation detail:
- Keep cleanup manually invoked only.
- Do not run cleanup during normal notification reads/writes.
Backend Notification Creation
Create notifications during upsert-comment only.
In handlePost, when mutation.type === 'upsert-comment':
1. Find target thread via existing findThreadEntryByCommentId(threadKeys, mutation.replyingTo).
2. Determine whether this is a new reply:
- !includesComment(entry.thread, mutation.commentId)
3. Get parent comment:
- entry.thread.commentsById[mutation.replyingTo]
4. Generate notification only if:
- It is a new reply, not edit.
- Parent comment exists.
- Parent comment has mutationOwner.
- Parent owner is different from reply owner.
- Parent owner is not anonymous.
5. Anonymous replies are allowed to notify signed-in parent owners.
6. Anonymous parent comments cannot receive notifications.
7. Store notification under parent owner’s signedUser.
Notification id format:
notification-{createdAt base36}-{random}
Suggested creation timing:
- Create after successful thread write.
- If notification write fails, do not fail the comment write. Log or include non-fatal behavior only.
- Avoid duplicate notification for idempotent retry by checking mutation.commentId newness before write.

Helpers:
fetchNotificationSummary(owner: MutationOwner): Promise<NotificationsSummaryResponse>
fetchNotifications(owner: MutationOwner, options?: { before?: number; limit?: number }): Promise<NotificationsListResponse>
markNotificationsChecked(owner: MutationOwner): Promise<NotificationsSummaryResponse>
fetchCommentsForLocations(requests: { locationId: ThreadLocationId; commentIds: CommentId[] }[]): Promise<Record<string, Record<CommentId, Comment | null>>>
Use headers for GET:
headers: {
  Authorization: `Bearer ${owner.signedUser}`,
  'X-Comment-User-Name': owner.userName,
}

Comment body resolver helper:
- Input shape is `(ThreadLocationId, CommentId[])[]`, represented in TS as `{ locationId: ThreadLocationId; commentIds: CommentId[] }[]`.
- Group/dedupe requests by stable location key so multiple notifications from the same chapter/paragraph trigger one thread fetch.
- For a paragraph location, call `fetchThreadsForLocation(locationId)`.
- For a chapter location, call `fetchThreadsForPage({ bookId, chapterId })`.
- Scan returned threads and resolve each requested id from `commentsById`.
- Return `null` for missing/deleted comments instead of throwing.
- Cache loaded thread data by location key within the helper call; later modal-level caching can reuse the same helper.

Loading Parent And Reply Text
Do not add GET /comments?notificationDetails=....
In the modal:
1. Build resolver requests from notifications:
- `{ locationId: notification.locationId, commentIds: [notification.parentCommentId, notification.replyCommentId] }`.
2. Call `fetchCommentsForLocations(...)`.
3. For each notification, read:
- parent comment from result[locationKey][parentCommentId]
- reply comment from result[locationKey][replyCommentId]
4. If parent or reply is missing/null, render a deleted/missing state.
Header UX
Add bell button in src/components/header.tsx.
Behavior:
- Only visible when logged in.
- On login/session restore, fetch summary once.
- No interval polling.
- Badge shows unread count.
- Cap badge label, e.g. 99+.
- Opening modal does not immediately clear “new” styling in the modal.
Modal UX
Create a notification modal component.
Behavior:
- Open from header bell.
- On first open:
- Fetch first 5 notifications.
- Store modalUnreadCutoff = lastCheckedAt if not already set.
- Call explicit markNotificationsChecked.
- Render notification as new if:
notification.createdAt > modalUnreadCutoff
- Keep modalUnreadCutoff until the user explicitly closes the modal.
- If the user clicks “Go to thread” and later reopens the modal, the same notifications still show as new until explicit modal close.
- On explicit close:
- Clear modalUnreadCutoff.
- Refresh summary.
- Badge reflects server state.
Display:
- Parent comment:
- one-line truncated by default.
- click to expand full text.
- Reply comment:
- full text.
- Metadata:
- actor name or Anonymous.
- relative timestamp.
- Unseen notifications:
- show a small border/accent.
- Infinite loading:
- fetch next page when near bottom or via “Load more” fallback.
- page size 5.
Deep Link / Go To Thread
Goal: navigate to exact thread location and highlight reply.
Chapter-level comment
For notifications without paragraphLocation:
1. Navigate to reader route for bookId/chapterId.
2. Include comment target in URL query/hash state, e.g. commentId=replyCommentId.
3. Ensure chapter comments are loaded even if lazy sentinel has not triggered.
4. Scroll to [data-comment-id="${replyCommentId}"].
5. Highlight target comment temporarily.
Paragraph-level comment
For notifications with paragraphLocation:
1. Navigate to reader route for bookId/chapterId.
2. Include paragraph/comment target in route state/query.
3. After reader content loads:
- open paragraph comment modal using stored paragraphLocation.
- load comments for that paragraph.
- scroll to [data-comment-id="${replyCommentId}"].
- highlight target comment temporarily.
Implementation notes:
- Add highlightedCommentId?: CommentId to CommentSection.
- Pass it to Thread.
- In Thread, set highlighted if either:
- comment belongs to current signed-in user, or
- commentId === highlightedCommentId.
- Consider separating visual classes so target highlight is stronger than “my comment”.
Patreon Stable User ID Task
Patreon API v2 identity response includes stable user id at:
userInfo.data.id
Current code ignores it and signs display name.
Task:
1. Add patreonUserId to OAuth response.
2. Add it to stored token and PatreonContext.
3. Change future signed identity to sign stable Patreon user id, not display name.
4. Keep display name separate.
5. Plan migration:
- Existing comments are keyed by old signedUser = HMAC(userName).
- A breaking switch would make old comments uneditable by the same user.
- Need dual identity support or a one-time migration strategy before changing comment auth.
Do not include this in the first notification implementation unless explicitly scoped in.
Edge Cases
- Parent comment deleted after notification:
- Modal shows “Original comment no longer exists.”
- Reply deleted after notification:
- Modal shows “Reply no longer exists.”
- Thread deleted:
- Modal shows “Thread no longer exists.”
- Anonymous parent:
- No notification generated.
- Anonymous reply:
- Notification generated if parent has signed owner.
- User replies to self:
- No notification generated.
- Notification write fails:
- Comment post still succeeds.
- User opens modal with zero notifications:
- Empty state.
- User opens modal, clicks Go to thread, reopens:
- Items still use original modalUnreadCutoff until explicit close.
